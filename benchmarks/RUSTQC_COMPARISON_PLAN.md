# Three-way comparison plan: upstream RSeQC, RSeQC-rust, RustQC

Prepared 2026-10-04. Task cards for LLM agents. The general agent rules, tiers
(S, M, L), standard checks and report format are in
[`docs/AGENT_PLAN.md`](../docs/AGENT_PLAN.md); read "Rules for every agent"
there first. This file replaces card E1 of that plan.

This is its own study. It is not the `protocol-v2.md` study and its numbers
must not be pooled with any other results in this directory.

## What is being compared

| Arm | Implementation | How it runs |
|---|---|---|
| U | upstream RSeQC 5.0.5 (`oracle/upstream-src`, `oracle/venv`) | one process per tool |
| P | this repository, `target/release` at a clean commit | one process per tool |
| R | RustQC (github.com/seqeralabs/RustQC), pinned release | one process for all tools, `rustqc rna` |

The comparison covers the eight RSeQC tools RustQC reimplements: `bam_stat`,
`infer_experiment`, `read_duplication`, `read_distribution`,
`junction_annotation`, `junction_saturation`, `inner_distance`, `tin`.

Two questions, answered separately:

1. **Equivalence:** for each tool, does P's output match U's, and does R's?
2. **Cost:** wall time, CPU time and peak memory to produce those eight outputs.

## Known facts and known unknowns about RustQC

Known (from its crate page and blog post, 2026-10-04): latest seen version
0.2.1; GPL-3.0-or-later; Linux x86_64 release tarball at
`https://github.com/seqeralabs/RustQC/releases`; invoked as
`rustqc rna <bam> --gtf <gtf> --paired --outdir <dir>`; takes a GTF, not a
BED12; processes chromosomes in parallel; also runs non-RSeQC tools (dupRadar,
featureCounts, preseq, Qualimap, samtools stats) in the same pass; describes its
outputs as "format- and numerically identical to the upstream tools".

Unknown, to be established by card R1 and R3, not guessed: the thread flag, any
flags to run only a subset of tools, strandedness flags, output filenames, and
which RSeQC version it was validated against.

## Fairness rules (binding on every card)

1. The same BAM, byte for byte, goes to all three arms. U and P get the BED12;
   R gets the GTF the BED12 was derived from. Card R2 proves the two describe
   the same transcripts.
2. Each arm uses its documented defaults, with options set equal where the
   tools expose the same option (MAPQ cutoff, sample size, strandedness).
   Every option given to every arm is recorded.
3. R does work the others do not (the non-RSeQC tools) unless it can be told
   not to. If it cannot, that is stated beside every R number.
4. R is multi-threaded and single-pass by design. It is measured at 1 thread
   and at 8 threads. P is measured sequentially and with its eight processes
   launched concurrently. All four configurations are reported.
5. Every result is published, including every row where P loses. Expect R to
   win total wall time at 8 threads; the plan is not designed to avoid showing
   that.
6. A "differs from upstream" verdict about RustQC is a public claim about
   someone else's software. Before it is recorded, the agent must rule out an
   option mismatch and an annotation mismatch, and must save the two differing
   files and a minimal description of the difference.
7. This machine is shared (16 logical CPUs, 31 GB). Every result file records
   the load average at the start of each run, and the published table says
   "shared hardware".

## Cards

Order: R1 → R2 → R3 → (R4 and R5 in parallel) → R6 → R7 → R8.

### R1. Install RustQC and record what it is (tier S)

- **Files:** `benchmarks/rustqc-comparison/tools/tools.json`,
  `benchmarks/rustqc-comparison/tools/rustqc-help.txt`, `.gitignore` (one line
  ignoring `benchmarks/rustqc-comparison/tools/rustqc`).
- **Steps:**
  1. Find the latest release tag on
     `https://github.com/seqeralabs/RustQC/releases` and download that exact
     tag's `rustqc-linux-x86_64.tar.gz` (a versioned URL, not `latest`) into
     `tools/`. No `sudo`, nothing installed outside this directory.
  2. Write `tools.json`: tag, download URL, tarball SHA256, binary SHA256,
     output of `rustqc --version`, date.
  3. Write `rustqc-help.txt`: the verbatim output of `rustqc --help` and
     `rustqc rna --help`, and of `--help` for any other subcommand listed.
- **Acceptance:** paste `rustqc --version` and the full `rustqc rna --help`.
  Do not summarise or interpret the flags.
- **If the download fails:** report the exact error and stop. Do not build from
  source or use a different version without being told to.

### R2. Workload manifest and annotation agreement (tier M)

- **Files:** `benchmarks/rustqc-comparison/workloads.json`,
  `benchmarks/rustqc-comparison/check_annotation.py`.
- **Steps:**
  1. For each workload record: paths, SHA256 of BAM, BED12 and GTF, record
     count, contig count, whether the BAM is coordinate-sorted and indexed,
     whether it is paired-end, whether duplicates are marked (count of records
     with flag 0x400).
  2. `check_annotation.py` compares BED12 and GTF: the set of transcript IDs,
     and for each shared transcript its chromosome, strand, start, end and exon
     blocks (BED is 0-based half-open, GTF is 1-based inclusive). It prints
     counts of: only in BED, only in GTF, shared and identical, shared but
     different, and exits non-zero unless both "only" counts and the
     "different" count are zero.
- **Acceptance:** output of `check_annotation.py` for rat and human.
- **If the sets differ:** do not fix anything. Report the counts and five
  example IDs from each category. The orchestrator then decides whether to
  derive a matching GTF subset or BED12 (`datasets/make_bed12.py`).

### R3. Option and output mapping (tier M)

- **Files:** `benchmarks/rustqc-comparison/output-map.json`.
- **Steps:**
  1. Using `rustqc-help.txt` only (not memory, not the web), determine: the
     thread flag; whether tools can be individually enabled or skipped; the
     strandedness, MAPQ and sample-size options.
  2. Run all three arms once on W-rat-3c into separate scratch directories.
     Commands for U and P are the eight tools with upstream defaults; take the
     exact invocations from `verification/run_diff.py` cases of the same names.
  3. For each of the eight tools write: the U command line, the P command
     line, the R options that correspond, each arm's output files and streams
     that carry the result, and which U options have no R equivalent.
  4. Record separately every R output file that belongs to a non-RSeQC tool,
     and whether those tools could be switched off.
- **Acceptance:** `output-map.json` plus a directory listing of each arm's
  scratch output. No equivalence judgement in this card.

### R4. Equivalence script (tier M)

- **Files:** `benchmarks/rustqc-comparison/equivalence.py`,
  `benchmarks/rustqc-comparison/test_equivalence.py`.
- **Design:** reads `workloads.json` and `output-map.json`, runs the three arms
  on one workload, and for each tool compares P to U and R to U. Reuse
  `verification/comparators.py`; do not write a new numeric comparator. Verdict
  per file, in this order:
  - `byte-identical`
  - `numerically-identical` (same structure, every number equal after parsing,
    differing only in formatting or whitespace)
  - `within-tolerance` (state the largest absolute and relative difference;
    tolerance is a command-line argument with default 0)
  - `differs` (record the first 20 differing lines and the largest difference)
  - `missing` (file or stream absent in one arm)
  - `not-comparable` (documented reason, for example a stochastic sampling
    step; `junction_saturation` shuffles, see `compatibility/divergences.yaml`)
  Files that exist only because of R's layout (extra summaries, plots, R
  scripts) are listed, not judged.
- **Tests must show failure:** a changed digit gives `differs`; a deleted file
  gives `missing`; two empty directories do not give any passing verdict; a
  NaN in place of a number gives `differs`.
- **Acceptance:** test output, and the verdict table for W-rat-3c.

### R5. Timing script (tier M)

- **Files:** `benchmarks/rustqc-comparison/timing.py`,
  `benchmarks/rustqc-comparison/test_timing.py`.
- **Configurations:**

  | ID | What is timed |
  |---|---|
  | U-seq | eight upstream tools, one after another; per-tool and total |
  | P-seq | eight port tools, one after another; per-tool and total |
  | P-par | eight port tools started together; batch wall time, aggregate memory |
  | R-1 | one `rustqc rna` run, 1 thread |
  | R-8 | one `rustqc rna` run, 8 threads |

- **Measurement:** wall, user and system time and peak RSS per process from
  `/usr/bin/time -v`. For P-par, aggregate memory sampled the way
  `verification/measure_concurrency.py` does it (baseline taken before
  anything starts). Environment pinned as in `benchmarks/bench.py`
  (`OMP_NUM_THREADS=1` and the other thread variables, `PYTHONHASHSEED=0`) for
  U and P; R gets only its own thread flag.
- **Schedule:** repetitions are blocks; inside each block the configurations
  run in a random order from a recorded seed. One unrecorded warm-up read of
  the BAM (`cat file > /dev/null`) before the first block.
- **Repetitions:** argument `--reps`, and a separate `--reps-upstream`, because
  upstream `tin` on a whole genome can take hours.
- **Timeouts:** per-process, using a retained `Popen` in its own process group
  (copy the pattern from `benchmarks/bench.py`; never `killpg(getpgid(0))`). A
  timeout is a recorded row, not a crash and not a dropped row.
- **Each run's JSON records:** configuration, workload, block and order, exact
  argv, exit status, the four measurements, load average before the run,
  binary SHA256, `git rev-parse HEAD` and whether the tree is dirty, RustQC
  tag, and whether the outputs passed `equivalence.py`'s file-presence check.
- **Tests:** a mocked timeout leaves the harness alive and writes a row; a
  failed process is recorded with its exit status; block order is reproducible
  from the seed.
- **Acceptance:** test output, and one `--reps 1 --reps-upstream 1` run on
  W-rat-3c completing with five configuration rows.

### R6. Run the study (tier L, orchestrator, not delegated)

1. Commit R1 to R5. Build `cargo build --workspace --release --locked` on that
   clean commit. Nothing else heavy may run on the machine during the study.
2. Equivalence on all three workloads.
3. Timing:

   | Workload | `--reps` (P and R) | `--reps-upstream` | Per-process timeout |
   |---|---|---|---|
   | W-rat-3c | 5 | 3 | 1 h |
   | W-hum-3c | 5 | 3 | 1 h |
   | W-rat-wg | 5 | 1 | 12 h |

4. Raw JSON goes to `raw/` and is committed unedited.
5. If a run is disturbed (load average above 4 before a block), repeat that
   block and keep both, marking the disturbed one.

### R7. Report generator (tier M)

- **Files:** `benchmarks/rustqc-comparison/report.py`,
  `benchmarks/rustqc-comparison/RESULTS.md` (generated).
- **Rules:** every number in `RESULTS.md` comes from `raw/` through
  `report.py`; nothing is typed by hand. Medians with min and max; an interval
  only where there are at least five repetitions; a single upstream repetition
  is labelled as a single run.
- **Sections, in this order:**
  1. Versions, hardware, "shared hardware" warning, date, commit.
  2. Scope table: tools covered by each implementation (33, 33, 8).
  3. Equivalence table: tool × workload, verdict for P and for R.
  4. Total cost for the eight tools: five configurations × three workloads,
     wall, CPU and peak memory.
  5. Per-tool U against P.
  6. What R's time includes that the others do not, from `output-map.json`.
  7. Limitations: three workloads, one machine, one RustQC version, no human
     whole genome, options with no equivalent.
- **Acceptance:** `report.py` run twice gives an identical file. The report
  contains every configuration row, including losses.

### R8. Publish in the repository docs (tier S)

- **Files:** `README.md`, `CHANGELOG.md`, `docs/MANUSCRIPT_OUTLINE.md`.
- **Steps:** add a short "Comparison with RustQC" section to the README
  containing sections 2, 3 and 4 of `RESULTS.md` copied exactly, the shared
  hardware warning, and a link to the full file. Replace the "to be measured"
  cells in the manuscript outline's related-work table. Add a CHANGELOG entry.
  No adjectives about either tool; the tables carry the result.
- **Acceptance:** `diff` showing the copied tables match `RESULTS.md`.
